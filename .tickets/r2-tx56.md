# Encrypt newly saved credentials with OS-protected key and add legacy-security UX

Implement opt-in encryption at rest for saved storage-provider credentials, backed by a per-install data-encryption key (DEK) held in the operating system credential store.

Current state: `uploads-turso.db` is a local Turso/SQLite-compatible database and persists R2 API tokens plus R2/AWS/MinIO/RustFS access and secret keys in plaintext. The database is protected only by normal OS file permissions.

Desired rollout: new users are secure by default. Existing users retain working legacy plaintext credentials unless they deliberately remove/re-enter them; do not automatically migrate or silently rewrite their existing credentials.

Scope:
- Use native secure credential stores for the DEK: macOS Keychain, Windows Credential Manager, Linux Secret Service/keyring. Evaluate/configure Rust `keyring` with required cross-platform features, including a supported Linux build/deployment story.
- Generate a cryptographically random 256-bit DEK once per installation, and store it only in the OS credential store. Never store it in SQLite, application config, logs, or error messages.
- Use a vetted authenticated-encryption primitive (AEAD; e.g. AES-256-GCM or XChaCha20-Poly1305), with a fresh nonce per encrypted value. Bind ciphertext to stable associated data such as provider/account/field identity so encrypted values cannot be swapped between records.
- Add an explicit secret-storage format/version to permit mixed legacy plaintext and encrypted records. Encrypt all newly created or edited R2, AWS, MinIO, and RustFS credentials. Do not fall back to plaintext if credential-store access/encryption fails.
- Keep non-secret account/bucket configuration, listings/cache, and transfer state plaintext unless there is a specific reason otherwise.
- Update reads/writes in `src-tauri/src/db/` so legacy entries remain usable and encrypted entries are decrypted only when needed.
- Protect sensitive values in diagnostics/errors and minimize plaintext lifetime in memory where practical (consider `zeroize`).
- Audit frontend-to-Tauri credential payloads and document that this ticket protects data at rest, not credentials used by the running application.

## Design

### Required technical decisions

- Encrypt every persisted credential value: R2 `api_token`, R2/AWS/MinIO/RustFS `access_key_id`, and `secret_access_key`. Access-key identifiers are sensitive metadata and must receive the same protection as secret keys.
- Use an explicit, versioned storage format for each credential-bearing record. Add a `credential_format` or `credential_version` column (or a dedicated credential table); do not infer encryption from a string prefix. The encrypted representation must be binary-safe and include/identify the format version, AEAD nonce, and ciphertext. This is required for legacy dispatch and future algorithm/key rotation.
- Bind AEAD ciphertext using an AAD encoding with its own version and only immutable identifiers: provider, immutable account ID, and credential field name (for example, `v1|aws|<account-uuid>|secret_access_key`). Never use account names, endpoints, bucket names, or other mutable configuration. For R2 records whose current integer token ID is allocated by SQLite, choose an implementation that makes the AAD identity available before encryption (for example an application-generated stable credential ID/a dedicated credential table, or allocate the record before encrypting).
- Encrypt with a fresh nonce for every field write. Treat AEAD authentication/AAD failure as a credential error; never attempt to interpret the value as legacy plaintext after such a failure.
- Use deterministic native-keychain service/account identifiers and centralize keychain access. Key lifecycle is fail-closed:
  - create and store the per-install DEK only when there are no encrypted credential records;
  - if encrypted records exist but the key is missing, corrupted, wrong-sized, locked, or otherwise unavailable, do not create or replace a key, do not decrypt or save credentials, and present recovery guidance to re-enter credentials;
  - distinguish a truly new install from a lost-key install, including when a database backup is restored without its OS-keychain entry;
  - handle concurrent first writes safely so they cannot establish competing keys.
- Keep decryption out of normal account/token list and Settings responses. Split non-secret account metadata from an internal, on-demand credential resolver used only when constructing provider/S3 clients or executing an operation that requires credentials. Do not send decrypted saved credentials to the frontend merely to render account lists.
- Provide a small internal key-store wrapper/module, primarily to centralize keychain naming, lifecycle, and error mapping. A broad injectable keychain test framework is not required for this ticket: crypto/format tests may use a fixed test key directly, and key-lifecycle behavior may use a lightweight fake where useful.
- Treat Linux keyring support as an explicit release requirement. Before committing the dependency/configuration, verify the selected Rust `keyring` backend and application packaging on the actual supported Linux targets. Document supported environments/dependencies and provide actionable UI when Secret Service/keyring or DBus is absent, locked, or unavailable. No plaintext fallback is permitted.
- Account/token removal must delete active credential records/references. State accurately that this does not guarantee removal from historic SQLite pages, WAL/journal files, backups, or copied databases; do not claim secure or forensic-grade erasure.

### Delivery milestones

1. **Crypto, format, and key lifecycle** — select vetted AEAD and keyring configuration; implement the key-store wrapper, versioned format, immutable AAD construction, encryption/decryption, and missing-key/error semantics. Add unit tests for format dispatch, tampering, AAD mismatch, nonce handling, and new-vs-lost-key lifecycle decisions.
2. **Database and provider integration** — update all R2/AWS/MinIO/RustFS credential writes to encrypt `api_token`/access-key IDs/secret keys; preserve legacy reads; refactor DB models and command paths so list/UI responses carry metadata only and credential resolution is on demand. Cover create, edit, delete, and current-provider/client construction paths.
3. **Legacy and recovery UX** — implement first-launch legacy detection, acknowledgement persistence in non-sensitive `app_state`, persistent Settings status/action, and clear unavailable/locked/missing-key recovery messages. Ensure new installations do not see the warning.
4. **Release validation** — run automated coverage and manual QA on macOS Keychain, Windows Credential Manager, and supported Linux keyring environments; verify packaging/deployment dependencies and document data-at-rest scope plus backup/restore and deletion limitations.

## Legacy-user UX

On first launch of the version containing this feature, detect whether any legacy plaintext credential records exist. If so, show a one-time explanatory modal:

- Existing accounts remain functional, but their saved credentials are stored using the older unencrypted format.
- New and newly edited/re-added credentials use protected/encrypted storage.
- To fully upgrade, remove each saved provider account/token and re-add it with the same credentials.
- Deleting/re-adding improves the active database state but cannot guarantee scrubbing historic SQLite pages, WAL/journal files, OS backups, or previously copied DB files. Recommend credential rotation if prior exposure is suspected.

Persist modal acknowledgement in non-sensitive `app_state`. Also expose a persistent Settings security status/action when legacy records remain (for example, “Legacy unencrypted credentials detected”), rather than repeatedly showing the modal.

New installations with no legacy credential rows must not see the legacy warning. Keychain unavailable/locked behavior must be explicit and actionable; saving a new credential should fail safely rather than save it unencrypted. Define recovery behavior for a missing/deleted keychain key (typically re-enter credentials) and document backup/restore implications, since a DB backup may not have its matching OS-keychain entry.

## Data-removal note

Ensure account/token removal deletes its credential material from the active DB and relevant record references. Do not claim forensic-grade secure erasure. Consider whether an optional future “rebuild local database” action is warranted, but do not broaden this ticket unless needed for correctness.

## Acceptance Criteria

- [ ] New R2, AWS, MinIO, and RustFS credentials are encrypted before persistence; plaintext secret fields cannot be recovered by opening a newly created `uploads-turso.db` with a SQLite-compatible viewer.
- [ ] Encryption key is random, 256-bit, stored solely in the native OS credential store, and is not logged or stored in the DB.
- [ ] Encrypted data uses authenticated encryption with unique nonces and stable associated data.
- [ ] Existing plaintext credential records continue working without automatic migration.
- [ ] Legacy detection produces a one-time modal only for installations containing legacy credential records; acknowledgement is persisted.
- [ ] Settings clearly reports remaining legacy credentials and explains the remove/re-add upgrade path and its erase/backup limitations.
- [ ] New installs do not receive the legacy warning.
- [ ] Credential-store unavailable/locked and missing-key scenarios have tested, understandable failure/recovery UX; no plaintext fallback occurs.
- [ ] Provider/account deletion removes associated active credential records.
- [ ] Automated tests cover encryption/decryption, tamper/AAD failure, format-version dispatch, legacy compatibility, new-write behavior, and modal-detection state. Add platform/manual QA notes for macOS, Windows, and Linux keychain behavior.
- [ ] No credential value appears in logs, errors, test snapshots, or debug output.
